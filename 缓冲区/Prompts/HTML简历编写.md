# HTML 简历编写 Prompt

> 执行方式：把本仓库作为工作目录打开 agent，让它执行本文件，参数在请求中一并给出。文件内的相对路径均以仓库根目录为基准。

## 调用参数

执行时在请求中一并给出已知参数。未提供的安全版式偏好采用默认值，不要为了可合理推断的选项中断工作。

```text
目标：泛用简历（默认）/ 岗位、项目或申请名称
岗位需求：粘贴 JD、申请要求或填写“无”
语言：中文 / 英文
参考已有简历：无（默认）/ 文件路径；可注明“版式与风格参考”“内容取舍参考”或“增量更新基线”。用户手工修改过的上一版成品同样有效，其中的措辞、句式和节奏属于其表达偏好
经历更新线索：无（默认）/ 用户指定经历或内容区文件 / Git 未提交改动 / Git 提交、提交范围或日期范围
输出目标：网页（默认）/ PDF / 网页和 PDF
展示模式：screen（个人主页）/ print（打印）/ both（默认）
打印篇幅：严格单页（默认）/ 允许多页 / 不适用
投递场景：公开发布（默认）/ 直接投递
字体：自动（默认）/ 无衬线 / 有衬线 / 混合
照片：不使用（默认）/ 仅网页 / 仅打印 / 全部使用，路径为……
联系方式：按场景自动（默认）/ 明确列出允许使用的字段
内容密度：舒适（默认）/ 标准 / 紧凑
颜色主题：模板默认 / 单色 / 指定颜色
页面尺寸：A4（默认）/ Letter
浏览器：Microsoft Edge（默认）/ 其他 Chromium 浏览器
个人主页集成：独立页面（默认）/ 提供可嵌入片段 / 接入现有网站，路径为……
输出格式：HTML、CSS、JS（默认）/ 另含 PDF
输出位置/名称：可选
额外要求：可选
```

参数解释：

- `screen` 不存在单页或多页限制，目标是响应式、易浏览和可扩展。
- `print` 才应用纸张尺寸与分页规则。
- `both` 必须由同一份语义化 HTML 和共享内容生成屏幕版与打印版，不复制两套正文。
- `严格单页` 同时表示页数上限和页面利用目标；`允许多页` 仍须控制分页质量。
- 当主要输出目标包含 PDF 时，具体简历默认打开 `print` 预览，使浏览器初始视图与最终 PDF 尽可能一致；个人主页或仅网页输出仍默认使用 `screen`。

## 提示词正文

你正在根据本知识库中的个人事实与 HTML 模板，制作一份可公开展示或实际投递的简历。请完成事实读取、内容选择、自然语言重写、HTML/CSS/JS 编写、Edge/Chromium 预览、打印检查和交付，而不只是给出建议。

### 一、理解目录和事实来源

1. 阅读根目录、`内容区`、`缓冲区`及相关父目录 README。
2. 先阅读 `内容区/索引.md` 定位可能相关的材料。索引只提供链接和少量导航元数据，不是事实来源，也不得被直接扩写成简历表述。
3. 内容区原始记录是个人事实与复盘的唯一来源。入选经历必须阅读其原文，理解个人贡献、完成状态、用户评价和公开限制后再重新组织语言；索引与原文不一致时以原文为准。
4. 索引未列出的经历不能据此判定为不存在；目标需求可能涉及遗漏材料时，应搜索内容区补充定位。
5. 成绩、排名、奖项等到 `内容区/事实资料` 核验。既有简历、输出网页和模板示例均不得反向作为事实来源。
6. 读取 `缓冲区/HTML/templates` 下的模板、样式、脚本和说明；模板仅负责结构与视觉表现。
7. 若提供“参考已有简历”，读取其可用的 HTML、CSS、PDF 或其他源文件，并按参数指定用途使用：
   - 版式与风格参考：借鉴视觉语言、栏目层级、响应式策略和打印密度，不继承其中的个人事实；
   - 内容取舍参考：理解用户过去重视的经历和表达方式，但仍须针对当前目标重新判断；
   - 增量更新基线：尽量保留未受影响且仍合适的页面结构、样式和正文，重点更新发生变化的部分，避免无理由重写整个版本。用户在成品中手工修改过的措辞、句式和节奏视为其表达偏好，除非与当前目标、事实或版式约束冲突，否则应保留而不是改回自己的写法。
   参考简历中的每项事实仍须由当前内容区原文支持；旧简历与内容区冲突时，以内容区为准。
8. 若提供“经历更新线索”，先用它缩小检查范围：用户明确指出的经历或文件优先；指定使用 Git 时，可通过只读的 `status`、`log` 和 `diff` 定位内容区中新增、修改、移动或删除的材料。Git 差异只说明“哪里发生变化”，不是独立事实来源；必须阅读变化后文件的完整当前内容，必要时再结合历史版本理解变更含义。
9. 没有更新线索时按目标正常读取索引和相关原文，不要求为了形式完整而遍历 Git 历史。用户提供的线索也不限制必要的上下游核验，例如奖项、时间、公开边界或同一经历的关联文件。
10. 经历目录中的赛题、报告、论文、演示文稿、代码说明等属于支撑材料。它们可用于核对项目背景、技术路线和项目整体结果，但不能仅凭团队报告把某项工作认定为个人贡献；简历中的主语、职责强度和成果归属仍以个人原始记录为准。

### 二、保护事实和隐私边界

- 不创造或夸大职责、成果、数字、排名、职位、技能、时间和因果关系。
- 团队成果不能直接写成本人贡献；只有来源明确支持时才使用“主导”“负责”“独立完成”等词。
- `【待定】`、未经确认的信息和模板占位内容不得进入成品。
- 未完成、失败或探索性经历只有在目标确实需要且状态能被准确表达时才使用。
- 未发表研究只呈现允许公开的问题框架和个人思考，不泄露受限细节。
- 英文内容应自然、克制地重写，不逐字翻译中文。
- 公开网页默认隐藏电话、私人邮箱、详细地址、照片及其他不必要身份属性；直接投递版只使用用户明确允许的字段。
- 不得在 HTML 注释、`data-*` 属性、JSON、JavaScript、源码映射或隐藏 DOM 中保留被隐私模式排除的信息。隐藏敏感信息不是删除敏感信息。

### 三、选择和组织内容

- 先提取目标要求中的能力、方法、领域和硬性条件，再选择真实证据。
- 优先级通常为：明确且相关的个人贡献 > 量化结果 > 有证据的方法与工具 > 项目背景。
- 根据经历本身选择分点逻辑，不对所有项目机械套用同一公式：
  - 对“职责较明确、独立工作内容较少”的项目，可按“必要背景／角色与团队边界 → 实际工作与技术方法 → 关键难题及针对性改进 → 结果与量化比较”组织。背景通常合并为一条，团队构成仅在有来源且能说明个人边界时写；结果优先写预测精度、效率、覆盖率、误差、规模或相对 benchmark 的变化，比赛名次和奖项放在标题辅助信息中，不冒充工作结果。
  - 对“包含多个相对独立任务、模块或问题”的项目，应按真实任务链或模块拆分，每条说明所处理的问题、采取的方法及可验证结果；例如开发项目不必为了形式完整另设一条泛泛的背景说明。
  - 可在确实有助于扫描时使用“职责”“方法”“难点与改进”“结果”等短标签，但标签不是必填项，也不得让每个项目变成僵硬的模板作文。
- 主要经历在事实充分时通常至少使用两条互补要点，分别说明角色／贡献与行动、方法或结果；不得把材料充足的项目压缩成一句话。
- 事实只够一条简短描述时，先判断其是否值得进入主要区域；不得拆句、重复或虚构来凑条目。
- 严格单页出现明显留白时，先把最相关的核心经历补足到“问题—方法—改进—结果”所需的信息密度，再考虑加入较弱经历或单纯放大间距；反之也不能把参考简历的高密度表达原样压进页面，必须保留可快速扫描的层级和呼吸感。
- 同一项目的标题、辅助信息和要点组成一个视觉单元；项目内最紧密，不同项目之间更宽，栏目之间最宽。
- 同一级灰色辅助信息位置必须统一：空间允许时默认放在标题下方；紧凑打印版可由模板整体切换为侧排，但不得逐条混用。
- 逐条检查换行。多行内容的末行原则上至少达到可用行宽约四分之一，绝大多数应达到约二分之一；避免集中出现一两个词的短尾行。
- 技能栏只保留正文有证据或事实资料可核验的技能，避免与经历和荣誉重复堆叠。

### 四、生成结构化、可复用的 HTML

1. 使用语义化结构：`header`、`main`、`section`、`article`、标题、列表、时间和链接；不要用大量无意义 `div` 或表格模拟全部布局。
2. 内容与表现分离：
   - HTML 保存本次简历正文和语义结构；
   - CSS 负责主题、响应式布局和打印分页；
   - JS 只负责模式切换、可选诊断和必要增强，不应成为基本内容可见的前提。
3. 优先复制模板目录生成具体版本，不把个人信息写回模板；具体版本应位于调用参数指定位置，未指定时放入 `output/HTMLOutput/<名称>/`。
4. 同一份 HTML 同时支持：
   - `data-view="screen"`：连续网页，不显示纸张阴影或强制分页；
   - `data-view="print"`：显示 A4/Letter 页面预览，并应用打印规则。
   当输出目标包含 PDF 时，将具体简历的默认视图设为 `print`；这只决定初始预览，不删除 `screen` 模式，也不要求个人主页模拟纸张。
5. `screen` 模式：
   - 使用响应式宽度，在手机、平板和桌面上均可读；
   - 不为了模拟纸张设置固定页面高度；
   - 允许更完整的内容、项目链接和后续个人主页组件，但避免默认折叠核心经历；
   - 键盘操作、链接焦点和颜色对比应可用。
6. `print` 模式：
   - 使用 `@page`、毫米单位和 `@media print` 控制纸张；
   - 关闭无关控件、纸张阴影、动画和背景装饰；
   - 对 `article`、标题与首条要点设置合理的 `break-inside`、`break-after` 或预留空间规则；
   - 不使用绝对定位堆叠正文，不通过固定高度裁掉内容；
   - GitHub、知乎、个人主页等链接只显示简洁且有意义的名称，并把 URL 嵌入显示文字；除非目标明确要求，不自动打印“名称：URL”、裸 URL 或冗长路径。
7. 字体应提供可靠的本地字体栈。未经用户授权不要依赖外部 CDN；若使用项目内字体，确认许可并使用相对路径。
8. 所有视觉参数优先写为 CSS 自定义属性，例如字号、行高、项目间距、页边距和主色；调整密度时协调修改相关全局参数并保持语义层级，不要求机械地同比缩放，也不逐条打补丁。
9. HTML 应在禁用 JavaScript 时仍显示完整简历正文。

### 五、分别处理 screen 与 print

#### screen / 个人主页模式

- 目标是连续、响应式阅读，不检查“页数”。
- 桌面端可使用克制的卡片、时间轴、双栏元信息或悬停反馈，但不能削弱快速扫描。
- 移动端应回落为单栏；日期、地点和角色不得挤压标题或产生横向滚动。
- 打印专用的分页标记在屏幕模式下不得产生异常空白。
- 若接入个人主页，复用数据、颜色、字体与组件；不要把 A4 白纸预览直接当作主页主体。

#### print / PDF 模式

- 严格单页：先筛选内容，再压缩文字，最后才小幅调整全局字号、行高和语义间距；不得缩放页面截图或使用过小字体强塞。
- 页面过空：检查是否遗漏合适事实，之后适度放松全局行高与间距；不能用巨大标题或无意义留白填页。
- 允许多页：不主动拉长，但不得为了单页牺牲项目内容；避免项目标题、单个 bullet 或极少量尾部内容孤立到下一页。
- 使用 Edge/Chromium 打印时固定纸张尺寸、缩放 100%、边距由 CSS 控制，并关闭浏览器页眉页脚。

### 六、Edge/Chromium 验证

1. 在 Microsoft Edge 或与其兼容的固定 Chromium 渲染器中打开具体 HTML，不只阅读源码。
2. 根据实际展示模式选择检查范围：
   - `screen`：检查桌面约 1440px 和移动端约 390px；
   - `print`：检查浏览器打印视图和导出的 PDF；
   - `both`：同时检查上述屏幕视口与打印结果。
3. 确认无横向滚动、遮挡、溢出、断裂链接、不可见焦点、异常换行和过低颜色对比。
4. 当展示模式为 `both` 时，切换 `screen` 与 `print`，确认正文来源一致，差异只来自调用参数明确允许的显示、隐私和排版规则；单一模式任务不为完成形式检查而额外制作另一种成品。
5. 打印版需导出 PDF 后确认：
   - 页数符合参数；
   - 项目与要点未被不合理拆页；
   - 页面首尾没有孤立标题、单条尾项或大片无意义空白；
   - 文字可选择、复制和提取；
   - 链接仍可点击；
   - 字体、颜色和图标正常嵌入或回退。
6. 将浏览器中的 `print` 视图与导出 PDF 进行视觉对照；二者应使用相同的纸张尺寸、页边距、字体、行高、语义间距和分页规则。允许浏览器工具栏、页面阴影等非打印界面元素不同，不允许正文结构或分页结果无故变化。
7. 若模板提供诊断面板，应逐项判断 overflow、short-tail 和 page-break 警告是否对应真实视觉问题。诊断仅作线索，可能存在误报；不得为了清空警告而破坏正常版面，最终以打印预览、导出 PDF 和目视检查为准。

### 七、交付

交付可直接打开的 HTML、CSS 和必要 JS；若参数包含 PDF，同时交付由 Edge/Chromium 导出的 PDF。简要说明：

- 使用的语言、screen/print 模式和字体；
- 打印页数及页面尺寸；
- 照片与联系方式隐私策略；
- 针对目标所做的内容取舍；
- 若以“增量更新基线”为基础，说明保留了哪些原有表述、改动了哪些部分；
- Edge 中的查看／打印方式；
- 尚缺少且会影响质量的事实或资源。

不要在交付说明中重复粘贴整份简历正文。
